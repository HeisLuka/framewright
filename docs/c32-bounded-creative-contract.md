# C32 — Bounded creative contract v1

## Decision

The user-side LLM is a creative proposal generator, not a trusted runtime component.

The production boundary is:

```text
server-owned data -> ContextPack v1 -> user LLM -> CreativeProposal v1
                                        |
                                        v
                              deterministic hard validator
                                        |
                                  accept / reject
                                        |
                                        v
                          C27 NarrativePlan -> I05 compiler -> RenderSpec
```

The renderer never asks an LLM what a claim means and never silently repairs an invalid proposal.

## Why v1 does not accept arbitrary copy

A deterministic program cannot reliably prove that arbitrary natural-language copy is entailed by a set of facts. Adding an LLM judge at validation time would simply move nondeterminism into the trust boundary.

C32 therefore makes the safe operation explicit: `ContextPack` contains **trusted creative atoms** minted upstream from known account/book data. Every atom has:

- a stable `atom_id`;
- a semantic role (`hook`, `tension`, `payoff`);
- allowed C27 angle types;
- exact display text;
- one or more `source_fact_ids`;
- a bounded `spoiler_level`.

The external LLM may choose and compose IDs, pacing, reveal timing, CTA treatment, delivery profile, visual system, assets, and seed. It may not inject new display copy, URLs, file paths, HTML, scripts, or unknown fields into the proposal.

This is the central v1 trade-off: creativity lives in **selection and composition inside a finite capability space**; factual authority remains server-owned.

## ContextPack v1

Schema: `newboo-context-pack-v1`.

A pack is generated by the product backend from authoritative state and contains:

- scoped account identity;
- books with canonical title/author;
- machine-readable facts and their source references;
- trusted creative atoms derived/approved upstream;
- owned assets identified by IDs and SHA-256, never client file paths;
- allowed CTAs;
- creative/runtime capabilities exposed to the LLM;
- constraints such as spoiler budget and body-atom count;
- `context_pack_id`, revision, and canonical `context_hash`.

`context_hash` is SHA-256 over canonical JSON with only the `context_hash` field omitted. Object-key order therefore does not change identity.

The client must not be allowed to submit a replacement ContextPack as authority. On execution the server loads its own canonical pack by `context_pack_id` and verifies the proposal's `context_hash` against that exact revision.

## CreativeProposal v1

Schema: `newboo-creative-proposal-v1`.

The proposal is deliberately semantic, not layout-level. It selects:

- account and book scope;
- C27 angle type;
- trusted hook/tension/payoff atom IDs;
- reveal timing;
- CTA treatment and, when required, an allowed CTA ID;
- duration, fps, visual system, delivery profile, seed;
- owned asset IDs.

It does **not** contain arbitrary `text`, `copy`, `prompt`, `url`, `uri`, `path`, `file`, `html`, or `script` fields.

`proposal_id = nbp1_<sha256>` over canonical proposal JSON with only `proposal_id` omitted.

## Hard validation

Validation is fail-closed. No fallback template, nearest-match substitution, typo repair, model call, or semantic rewriting occurs after rejection.

The validator checks, in deterministic order:

1. schema/version and exact allowed fields;
2. ContextPack integrity and canonical hash;
3. exact `context_pack_id`, context hash, and account binding;
4. book existence inside the pack;
5. atom existence, same-book scope, semantic role, and allowed angle;
6. spoiler budget and body-atom count;
7. asset existence, same-book scope, and required cover selection;
8. capability allowlists for angle, duration, fps, visual system, delivery profile, reveal timing, and CTA treatment;
9. C27 cross-field grammar constraints, including 3s/5s behavior and 7s+ tension;
10. CTA existence/treatment rules;
11. proposal identity;
12. forbidden raw-content and unknown-field attempts.

Errors are sorted by JSON path, then error code, so the same invalid input produces the same error list.

Representative stable codes include `CONTEXT_HASH_MISMATCH`, `ACCOUNT_SCOPE_MISMATCH`, `UNKNOWN_BOOK`, `UNKNOWN_ATOM`, `ATOM_SCOPE_MISMATCH`, `ATOM_ROLE_MISMATCH`, `ATOM_ANGLE_MISMATCH`, `SPOILER_BUDGET_EXCEEDED`, `UNKNOWN_ASSET`, `ASSET_SCOPE_MISMATCH`, `CAPABILITY_DENIED`, `TENSION_REQUIRED`, `DURATION_CTA_CONFLICT`, `REVEAL_DURATION_CONFLICT`, `UNKNOWN_CTA`, `FORBIDDEN_RAW_CONTENT`, `UNKNOWN_FIELD`, and `PROPOSAL_ID_MISMATCH`.

## Compile bridge

An accepted proposal is converted to `newboo-accepted-creative-program-v1`.

Trusted atoms are translated to the existing C27 `human_verified` source form with deterministic provenance IDs:

```text
context:<context_hash>:atom:<atom_id>
```

The bridge then calls the existing C27 `planNarrative()` implementation. Book title/author remain canonical book payload fields. Explicit CTA copy is loaded from the server-owned CTA registry in the ContextPack. The accepted program retains presentation/asset selections for the downstream I05/RenderSpec compiler.

`program_id = nbprog1_<sha256>` over canonical accepted-program JSON. Proposal/context key ordering does not affect identity; a semantic selection change does.

## Threat boundary

C32 assumes the external LLM is untrusted and may hallucinate IDs, omit required data, output stale context, cross book/account boundaries, or attempt to smuggle arbitrary content. Those are ordinary validation failures, not exceptional cases.

C32 does **not** claim that the validator can infer whether arbitrary prose is true. Only server-minted atoms are factual render inputs in v1.

A future free-text mode must cross a separate trust boundary first, for example by producing a server-side verification/approval artifact whose ID and content hash can be referenced by CreativeProposal. Raw LLM prose must not bypass that boundary.

## Test gate

`node contracts/check-creative-proposal-v1.mjs` must pass and covers:

- valid ContextPack + CreativeProposal -> real C27 NarrativePlan;
- committed machine-readable examples;
- context/proposal/program identity under JSON key reordering;
- stale context hash;
- unknown and cross-book atom references;
- cross-book asset reference;
- unsupported capability;
- spoiler-budget violation;
- missing 7s+ tension;
- irrelevant body atoms in 3s/5s profiles;
- raw copy/URL injection attempts;
- unknown fields;
- unknown CTA;
- reveal/duration conflict;
- deterministic error ordering;
- semantic change -> different proposal/program identity.
